# YTMD Deckboard Extension Guide

## Overview

This extension lets Deckboard control YouTube Music Desktop 2 using the local API exposed by the YTMD app instead of the legacy remote-control server flow. It keeps the Deckboard button experience simple: each action maps to a YTMD HTTP route, sends the required authentication token, and updates the live status text when playback changes.

The extension is designed to run as a Deckboard extension package, and it is optimized for the current YTMD local API contract used by the default configuration.

## Deckboard extension metadata

The extension entry is defined in `extension.yml`:

```yaml
name: YTMD2-deckboard
package: YTMD2-deckboard
version: 2.0.1
description: An extension to interact with Youtube Music Desktop App through the ytmd2 API.
author: Ev
license: Apache License 2.0
repository: 'https://github.com/ev-1233/YTMD-deckboard'
```

The main package entry points to `index.js`, which is the file Deckboard loads when the extension is installed.

## Local API requirements

This extension expects the following setup in the local machine:

1. Deckboard is installed.
2. YouTube Music Desktop 2 is installed and running.
3. The local API is enabled in YTMD.
4. The YTMD API requires authorization.
5. A client token has been created and copied from the YTMD settings.

The default API base URL is:

```text
http://127.0.0.1:13091
```

You can override it through the `apiUrl` config in the extension settings if the YTMD instance is bound to another local port or address.

## Required configuration

The extension exposes two runtime configuration values inside the extension settings panel:

- `apiUrl`: YTMD local API base URL.
- `apiToken`: Authorization token for requests to the YTMD API.

The token is sent as:

```http
Authorization: Bearer <token>
```

The project includes a safety layer that redacts the token in debug logs so secrets are not leaked in console output.

## Extension lifecycle

The extension class extends the Deckboard `Extension` base and sets up:

- `this.name`: visible extension name
- `this.platforms`: supported operating systems
- `this.inputs`: available Deckboard buttons
- `this.configs`: runtime user settings
- `this.initExtension()`: initialization logic
- `this.execute(action, args)`: trigger handling for each button

The typical lifecycle is:

1. Deckboard loads the extension.
2. `initExtension()` reads the config values.
3. `refreshPlaybackState()` polls `/track/state`.
4. Deckboard updates button labels for playing and paused status.
5. A user action triggers `execute()`.
6. `postQuery()` maps the action to the correct YTMD route and sends the request.

## Action mapping

The extension uses a static `ACTIONS` map to convert each Deckboard button value into an HTTP call. For example:

```js
static ACTIONS = {
  'track-play': {
    method: 'POST',
    path: '/track/play',
  },
  'track-pause': {
    method: 'POST',
    path: '/track/pause',
  },
  'track-forward': {
    method: 'POST',
    path: '/track/forward',
    body: (config = {}) => ({ time: Number(config.time) || 10 }),
  },
};
```

This mapping makes the code easy to maintain and keeps the API contract localized in one place.

## Input definitions

Deckboard buttons are defined in the `this.inputs` array. Examples that ship with the extension include:

- Track play/pause
- Track play
- Track pause
- Track repeat
- Track shuffle
- Forward/backward 10 seconds
- Like/dislike
- Skip next/previous
- Home
- Clear queue
- Volume up/down

Each entry includes a label, action value, icon, and color, so the package is immediately usable in Deckboard without extra setup.

## Fetch and HTTP behavior

The extension wraps runtime fetching in a helper that:

- normalizes the API URL
- injects the bearer token if configured
- sends JSON bodies when relevant
- logs sanitized request/response metadata
- retries with fallback auth patterns if the server rejects a standard header

The most important response handling paths are:

- `getPlaybackState()`: polls the live playback status
- `postQuery()`: executes a Deckboard action against YTMD
- `tryAuthFallback()`: retries when YTMD accepts raw tokens or query-token auth
- `tryCommandFallback()`: retries alternate route names when a backend uses a nonstandard endpoint

## Debugging and diagnostics

The extension records helpful debug data in the console, including:

- request method and destination
- auth header status (redacted)
- request body payload
- response status and success flags
- route availability diagnostics when a YTMD call fails

Use this output when testing with a fresh YTMD install or when a route name differs from the expected API contract.

## Release workflow

Before publishing a build, run the project checks locally:

```bash
npm install
npm run check
npm run build
```

The package scripts are:

```bash
npm run lint
npm run lint:fix
npm run format
npm run format:check
npm run test
npm run check
npm run build
```

The `check` script runs formatting, linting, and test validation together and is the best local gate before release.

## Building the extension

The project uses the deckboard-kit build tooling to prepare a distributable Deckboard package.

```bash
npm run build
```

This produces the packaged extension in the `dist/` directory and strips unnecessary development files as part of the Deckboard packaging flow.

## Packaging guidelines

When preparing a release:

1. Confirm YTMD is running locally and the token is valid.
2. Run `npm run check` to confirm there are no linting or test regressions.
3. Run `npm run build` to create the packaged artifact.
4. Test the generated `.asar` package in Deckboard.
5. Confirm the extension loads with the configured YTMD URL and bearer token.
6. Verify the live playback status updates correctly.
7. Verify actions such as play, pause, next, previous, like, dislike, and volume control work as expected.

## Security notes

- Never commit real bearer tokens to source control.
- Do not expose tokens in screenshots or debug logs.
- Keep the extension URL in the local machine range rather than a remote host.
- Validate all user input before building API payloads.

## Troubleshooting

### Extension does not load

- Confirm `extension.yml` has a valid `package` name and version.
- Check that `index.js` is the `main` entry in `package.json`.
- Rebuild the package after changing configuration.

### Playback status shows unknown

- Confirm YTMD is running and the port is correct.
- Verify the API token is valid.
- Check that authorization is enabled in the YTMD auth settings.
- Make sure the API client is allowed for the local endpoint.

### Commands fail with HTTP 401

- Confirm the `Authorization` header is being set correctly.
- Check whether YTMD expects a raw token or a query string token.
- Re-run the extension in debug mode and inspect the redacted request output.

### Button actions do nothing

- Check the Deckboard action value matches the exact command name used by the extension.
- Verify the route exists in the running YTMD API.
- Confirm the token has permission to execute the relevant commands.

## Maintainer notes

This project is intentionally small and direct: most of the logic lives in one place so the extension is easy to debug and easy to ship. If new YTMD actions are added later, the recommended approach is to add the route to the `ACTIONS` map, include a dedicated test, and keep the request payload contract explicit.
